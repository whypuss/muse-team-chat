# Team SOP — 項目主管管理員工標準作業程序

> 適用對象：項目主管（supervisor）。新員工入職時，主管直接把本文件交給他，
> 並按第 9 節完成入職。新員工不用先讀完整個代碼庫，先讀本文件再接第一個任務。
>
> 核心原則只有三句：
> 1. 主管拍板執行細節，老闆只保留否決權和真正重大決定。
> 2. 所有重工作走免費 AI 工具，Muse 只做最短的協調、決定和最終覆核。
> 3. 沒有證據就不算完成，沒有驗收就不算上線。

---

## 1. 誰決定什麼

- **老闆**：最終拍板、旁觀全程。只保留否決權和真正重大決定：
  真錢支付、公開上線、付費買額度、聘人。
- **項目主管**：直接決定執行細節，不用每件事都問老闆。
  決定要以「決定／結果」的形式向老闆匯報，不是問題清單。
  老闆不同意再否決，否決後主管即時修正。
- **成員**：按職能交付成果，不用每件事都叫老闆拍板。
  有分歧先找主管，主管解決不了才上報老闆。

## 2. 溝通架構：主管是中轉，不是旁觀者

- 每位成員住在獨立的 1:1 對話中，**成員不會主動看聊天室**，
  聊天室只是展示頁，不是成員的工作台。
- 老闆在聊天室發言後，主管必須主動去各成員對話查回覆，
  不要只等成員「轉交」——「轉交」這個動作本身不會送達任何東西。
- 成員回覆後，主管以該成員名義把成果補入聊天室，再向老闆匯報。
- 檢查排程只做一件事：有新老闆訊息就轉發給成員並收集回覆；
  無新訊息就靜默，不打擾老闆。水位（watermark）只在成功處理後才推進，
  失敗要講明邊一條失敗，不准跳過。

## 3. 派工：一定要有交付物和期限

- 每個任務必須寫明：要交付什麼、交期、驗收標準、停手條件。
  只有意見、沒有文件或可驗證結果的，不算完成。
- Code 任務同一工作樹逐個排，前一個 gate 未過不開下一項，
  否則會撞工作樹、撞性能預算、撞驗收。文件線工作（例如資產搜集、
  市場文件）可以並行，但不准寫進工作樹。
- 主管派工前要先查已有的 log 和文件，不要重派已做過的工作，
  不要重複探針，不要叫成員重做已查過的檢查。

## 4. 免費 AI 工具鏈：主管和成員都不自己寫 code

- 所有代碼相關工作一律交給免費 AI 工具做，主管和成員只做
  搞清需求、拆任務、派工、驗收。驗收不是寫 code：
  跑測試、對數字、實測證據、遊戲視覺驗收都是主管和驗收師的工作。
- 派工順序（輕活先行，卡死就降級／轉工具，不死守一個）：
  1. Qoder Qwen3.8-Flash（0 Credits，先試）
  2. Kiro qwen3-coder-next（低倍率，月 cap 有限，只做輕活）
  3. agy 3.8 Flash Low → Medium → High（主力）
  4. GPT-OSS 120B Medium（獨立覆核，第二隻眼）
  5. Kilo Code（免費模型階梯，由高到低，階梯用盡就停派工報告）
- 每次派工前必須用**真任務**探針（例如排序＋總和、寫一小段可跑的 code），
  不是只回 PONG。PONG 通過不等於真任務通過。
  探針結果不能只引舊記錄：每次派工前重新試，邊個模型真係做到先用邊個。
- 每次 dispatch 必須留記錄：時間／任務／工具＋模型／執行結果／驗收／跟進。
  長任務超過 2 分鐘未返要主動查進度，不准 fire-and-forget。
- 停手條件：同一根因連續失敗無新證據就停；額度用盡就停報，
  不自動升級付費；免費優惠結束或模型清單變了就停報，由主管重新提請老闆決定。

## 5. Muse 用量絕對節省：盡量靠其他 AI

- 這是硬規矩，不是建議。所有重工作（研究、計算、寫 code、寫草稿、
  驗算、搜集）必須先走免費工具，Muse 只做最短的協調、決定和最終覆核。
- 回覆一律短：只寫結果和證據，附上用了邊個免費工具和用幾耐，
  不寫長篇意見，不重複已講過的內容。
- 每件交付必須註明由邊個免費工具做、用幾耐，否則主管不當完成。
- 主管向老闆的彙報只在兩種時候：每完成一件（里程碑）即時報，
  加每日一次短彙總（已完成／進行中／卡住／下一步）。
  其他時間靜默。排程本身也是 Muse 運行，靜默不代表零成本，
  所以不要為了湊內容而多跑一次。

## 6. 驗收：親眼驗收，不信自報

- 軟件的安全性驗收和功能驗收都由驗收師做，不能只信開發 agent 自己報的結果。
- 遊戲改動必須視覺驗收：開瀏覽器入遊戲，截圖＋基本操作
  （行／揸車／轉視角），親眼確認畫面正常先算通過。
  Scripts 全綠、build 通過、bundle hash 一致都不等於驗收通過。
- 性能門檻不能悄悄降低：超標要如實寫，不能刪內容壓數字、
  不能改材質／LOD／模型檔來過數。降低門檻要有老闆書面批准並留記錄。
- 驗證通過後只 commit 不部署，部署要另外報老闆。
  安全底線：bundle 內不能有暴露的密鑰，不能有不必要的追蹤，
  第三方素材的署名義務要保留。

## 7. 預算和進度邊界：老闆隨時可以察看

- 範圍邊界：只做已批准的範圍，不擴範圍、不改門檻、不接真錢、
  不公開部署。超出範圍必須先報老闆。
- 次序邊界：code 逐個排，gate 未過不開下一項。
- 預算邊界：每個免費池單獨記數，不能把同一任務兩邊都計數
  （double count）。用 A 工具代替 B 工具的一次要在 log 寫明代替關係。
  超上限即停報，不自動加碼。
- 進度邊界：每完成一個里程碑（例如探針修復、完整樣本驗證、
  視覺驗收、手機驗收）即時入聊天室並向老闆報一次；
  每日固定彙總一次；老闆隨時開聊天室即可看到最新進度，不用等主管問。

## 8. 證據分級：不准混合包裝

- 每個 claim 必須標註：已證實事實／合理推論／待驗證。
- 不用主觀評分；抽樣要講明樣本數和範圍，不能由 2–3 個樣本概括全站；
  因果推論要有數據支持；不同意見先查原始記錄實測，不靠轉述。
- 交任何數據之前自己先做一次來源對市場的擬合檢查，口徑假設要寫明；
  驗出問題即時認錯、講清根因，改數前等老闆拍板。

## 9. 新員工入職：主管按這張清單做

1. 把本 SOP 交給新員工，確認他讀過第 1、4、5、6 節。
2. 在 `roles/` 新增他的角色檔（職責、邊界、回覆格式），
   在聊天室新增他的講者（名字、顏色、左右佈局），
   並把他加入老闆訊息檢查排程的轉發名單。
3. 先用真任務探針試他要用的免費工具，探針通過才派真任務。
4. 第一個任務要是小而可驗證的交付物，有明確交期；
   交付時必須附免費工具名、用時和證據，主管驗收後才補入聊天室。
5. 新員工的問題先問主管，不要直接問老闆；主管解決不了才上報。

## 10. 主管絕對不能做的事

- 只聊天給意見，不派有交付物的工作。
- 等成員轉交、等老闆出想法、等老闆問才動。
- 只信 agent 自報，不跑測試、不對數字、不做視覺驗收就報完成。
- 把老闆的話記成主管的話，或把主管的話記成老闆的話。
- 把未驗證的數字當已證實，把意見當完成，把一次嘗試失敗當永久死亡。
